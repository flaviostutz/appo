# Data Model: Device Operations API and MCP Access

## DeviceIdentity

**Purpose**: Canonical address for any read, history, command, or registration decision.

**Fields**:
- `account_id`: tenant identifier
- `device_id`: device type/model identifier
- `device_instance_id`: unique instance identifier
- `node_name`: logical subsystem within the device
- `attribute_name`: concrete readable/writable attribute

**Validation**:
- All path segments are required for attribute-level operations.
- `device_instance_id` is generated by the server during registration and must be unique within `(account_id, device_id)`.
- `*` is valid only inside authorization scopes, never in persisted device identities.

## AccessScope

**Purpose**: Encodes which protected capability a bearer token grants.

**Fields**:
- `family`: `i` for device operations, `r` for registration
- `path_segments`: 5 segments for `i`, 2 segments for `r`
- `actions`: `r`, `w`, `s` for `i`; none for `r`

**Validation**:
- `i` scopes must match `account_id/device_id/device_instance_id/node_name/attribute_name:actions`.
- `r` scopes must match `account_id/device_id`.
- Wildcards match a whole segment only.
- Device-operation actions may contain only `r`, `w`, and `s`.

**Relationships**:
- Many `AccessScope` values may be attached to one bearer token.
- `AccessScope` authorizes access to one or more `DeviceIdentity` values depending on wildcard usage.

## DeviceObservation

**Purpose**: One persisted time-stamped reading stored in InfluxDB.

**Fields**:
- `measurement`: fixed `device_attributes`
- `identity_tags`: `account_id`, `device_id`, `device_instance_id`, `node_name`, `attribute_name`
- `value_float`: nullable numeric value
- `value_string`: nullable string value
- `value_bool`: nullable boolean value
- `timestamp`: observation time in milliseconds precision

**Validation**:
- Exactly one typed value field is populated per row.
- Tags must match the identity hierarchy already defined by the bridge XDRs.
- `timestamp` is bounded by the caller's `from`/`to` range in history reads.

## DeviceStateSnapshot

**Purpose**: Latest known reported state for a device instance.

**Fields**:
- `device_instance`: `(account_id, device_id, device_instance_id)`
- `attributes`: collection of latest `DeviceObservation` values keyed by `(node_name, attribute_name)`
- `is_partial`: boolean indicating that some attributes were excluded by authorization filtering

**Validation**:
- Contains at most one latest observation per `(node_name, attribute_name)`.
- `is_partial` is `true` when any stored attribute for the device instance was withheld from the caller.

## HistoryRange

**Purpose**: Explicit time bounds for history queries.

**Fields**:
- `from`: inclusive lower timestamp
- `to`: exclusive upper timestamp

**Validation**:
- Both timestamps are required.
- `from < to` must hold.
- Unparseable or inverted timestamps produce a validation error before querying storage.

## DesiredStateCommand

**Purpose**: Request to publish a target value to the device `/set` topic.

**Fields**:
- `identity`: target `DeviceIdentity`
- `payload_value`: scalar or JSON value compatible with the MQTT topic schema
- `topic`: `account/device/instance/node/attribute/set`
- `requested_by_scope`: authorizing `AccessScope`

**Validation**:
- Caller must have `s` access for the exact target identity or a matching wildcard scope.
- Command acceptance does not change `DeviceObservation` rows; the actual device must report the new state later.

## RegistrationGrant

**Purpose**: Stateless result of a successful registration request.

**Fields**:
- `account_id`
- `device_id`
- `device_instance_id`: newly issued identifier
- `credential`: one JWT limited to the new instance
- `credential_scope`: `i:account_id/device_id/device_instance_id/*/*:rws`

**Validation**:
- Caller must have `r:account_id/device_id` authorization.
- One registration request returns one new `device_instance_id` and one JWT.
- No server-side registration session is retained after issuance.

## Relationships

- `RegistrationGrant` creates a new `DeviceIdentity` root at the device-instance level.
- `AccessScope` controls visibility of `DeviceObservation`, `DeviceStateSnapshot`, and `DesiredStateCommand` operations.
- `DeviceStateSnapshot` is derived from many `DeviceObservation` rows.
- `HistoryRange` constrains which `DeviceObservation` rows are returned.

## State Transitions

### Registration

1. Caller presents `r:account_id/device_id` bearer token.
2. Server validates the scope.
3. Server generates a new `device_instance_id`.
4. Server signs one JWT scoped to `i:account/device/new-instance/*/*:rws`.
5. Server returns a `RegistrationGrant` and stores no registration session state.

### Desired-State Write

1. Caller presents an `i:` scope containing `s`.
2. Server validates authorization for the target `DeviceIdentity`.
3. Server publishes to the `/set` MQTT topic.
4. Current-state reads remain unchanged until a later `DeviceObservation` is ingested.

# MCP Tool Contract

The MCP surface must expose the same business capability as the REST API. Tool handlers call the same shared Go operations service used by the HTTP handlers.

## Tools

| Tool | Purpose | Required Input | Authorization | Result |
|------|---------|----------------|---------------|--------|
| `get_attribute_state` | Read latest value for one attribute | `account_id`, `device_id`, `device_instance_id`, `node_name`, `attribute_name` | Matching `i:...:r` scope | One latest observation or `found=false` |
| `get_device_state` | Read latest state snapshot for one device instance | `account_id`, `device_id`, `device_instance_id` | Matching `i:...:r` scopes for visible attributes | Snapshot with `is_partial` and visible attributes only |
| `get_node_history` | Read history for all authorized attributes under one node | `account_id`, `device_id`, `device_instance_id`, `node_name`, `from`, `to`, optional `cursor` | Matching `i:...:r` scopes | Ordered history page plus optional `next_cursor` |
| `get_attribute_history` | Read history for one attribute | `account_id`, `device_id`, `device_instance_id`, `node_name`, `attribute_name`, `from`, `to`, optional `cursor` | Matching `i:...:r` scope | Ordered history page plus optional `next_cursor` |
| `set_desired_state` | Publish desired value to the device `/set` topic | `account_id`, `device_id`, `device_instance_id`, `node_name`, `attribute_name`, `value` | Matching `i:...:s` scope | `accepted=true` and published topic |
| `register_device_instance` | Create a new device instance and return one scoped credential | `account_id`, `device_id` | Matching `r:account_id/device_id` scope | `device_instance_id`, JWT token, issued scope |

## Shared Rules

- MCP errors must mirror REST business failures: invalid input, unauthorized, forbidden, not found/empty result, and backend failures.
- Tool inputs use the same field names and validation rules as the REST contract.
- `get_device_state` must return `is_partial=true` when authorization filtered out stored attributes.
- History tools must reject missing, unparseable, or inverted `from`/`to` timestamps.
- `set_desired_state` acknowledges publication only; it does not imply the device has reported a new actual state.
- `register_device_instance` returns one JWT scoped to `i:account_id/device_id/device_instance_id/*/*:rws`.

## Transport

- MCP is served over HTTP from the same `stutzthings-server` process.
- The planned endpoint is `/mcp` on the same port as the REST API and `/health`.
- Authentication is handled before tool execution and uses the same bearer-token parsing and scope matcher as REST.

# Quickstart: Device Operations API and MCP Access

This quickstart describes the intended end-to-end verification flow for the feature after implementation lands.

## Prerequisites

- `mise`
- Docker Desktop or compatible `docker compose`
- A local JWT signing secret for development

## Start the local stack

```sh
cd stutzthings/stutzthings-server
make install
export JWT_SIGNING_SECRET=dev_jwt_secret_local_only_please_change
make run
```

Expected result:
- Mosquitto and InfluxDB start locally
- `stutzthings-server` starts on `:8080`
- `GET /health` returns `200` with bridge and API dependencies healthy

## Verify bridge ingestion prerequisites

If the local InfluxDB database is not already present, create it once:

```sh
cd stutzthings/stutzthings-server/examples/local
make create-database
```

## Exercise the REST API

Use a valid registration bearer token with scope `r:demo-account/demo-device`:

```sh
curl -X POST http://127.0.0.1:8080/registration \
  -H "Authorization: Bearer <registration-token>" \
  -H "Content-Type: application/json" \
  -d '{"accountId":"demo-account","deviceId":"demo-device"}'
```

Publish device telemetry to the broker, then read it back:

```sh
curl -H "Authorization: Bearer <device-read-token>" \
  "http://127.0.0.1:8080/demo-account/demo-device/<device-instance-id>/temperature/celsius"

curl -H "Authorization: Bearer <device-read-token>" \
  "http://127.0.0.1:8080/demo-account/demo-device/<device-instance-id>/temperature/celsius/history?from=2026-03-17T00:00:00Z&to=2026-03-17T01:00:00Z"
```

Publish a desired-state command:

```sh
curl -X PUT http://127.0.0.1:8080/demo-account/demo-device/<device-instance-id>/lamp/power \
  -H "Authorization: Bearer <device-set-token>" \
  -H "Content-Type: application/json" \
  -d '{"value":"on"}'
```

## Exercise the MCP endpoint

Connect an MCP client or inspector to `http://127.0.0.1:8080/mcp` and call:

- `get_attribute_state`
- `get_device_state`
- `get_node_history`
- `get_attribute_history`
- `set_desired_state`
- `register_device_instance`

REST and MCP results must match for the same authorization context.

## Verification commands

```sh
cd stutzthings/stutzthings-server
make test
make lint
```

For richer local observability, use the Grafana-based stack in `examples/local/`.
